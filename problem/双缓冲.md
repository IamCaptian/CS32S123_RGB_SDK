# RGB 屏整帧双缓冲问题记录

## 1. 背景与目标

- 屏幕：ST7701S，480×480，RGB565（PRGB16），`GUI_SELECT = GUI_LCD_480_ST7701S`。
- 目标：页面左右滑动切换时消除撕裂，实现整帧双缓冲。
- 现状：双缓冲仍未调通，本文记录已尝试方案、现象、根因分析、代码改动点和后续方向。

## 2. 当前显示架构（单缓冲）

- 驱动里只有一块整屏缓冲 `refersh_dma_buf`（`AT(.psram_buf.lcd)`，约 461KB），初始化时直接写进 `LCDADR`：
  - `platform/gui/tft/tft_480_st7701s_prgb.c`
  - `platform/gui/tft/tft_drv.c` 的 `lcd_drv_reg_init()`：
    - `LCDADR = DMA映射地址`
    - `gpu_share_tft_init(false, true, ramless_buf, GUI_SCREEN_WIDTH)`
- GUI 每帧通过 `tft_te_refresh()`（TICK1，约 16.7ms）调用 `os_gui_draw()`，GPU/DE 直接写这块 framebuffer，LCD DMA 同时扫描同一块 → 全屏动画时撕裂。
- 这块 RGB 屏没有 TE 引脚（`PORT_TFT_INT = IO_NONE`），刷新节拍靠定时器。
- GUI 是**增量绘制**：只画发生变化的区域，依赖 framebuffer 长期保留上一帧完整内容。

## 3. 已尝试方案与结果

### 方案 1：使用 SDK 预留的 `GUI_SPU_PSRAM`

- `config.h` 里 `GUI_SPU_PSRAM = 0`，`gui.c` 里预留了 `psram_gui_buff[两帧]` 和 `gui_flush_lcd_buff_get/put`。
- 打开后白屏。原因（反汇编 + `problem/psram.md` 记录）：
  1. 宏为 0 时 `gui_flush_lcd_buff_get()` 用库里弱符号，直接返回 NULL。
  2. 打开宏后由 `gui.c` 接管，但 `buff0_idx/buff1_idx` 没有任何地方置 1，仍然永远返回 NULL。
  3. `os_gui_flush_lcd()` 全工程没有调用者；打开 user psram 后 GUI 线程会跳过 `tft_frame_start/end`，没人触发翻页。
  4. 只补 get/put 也不够：GPU 绘制目标只有一块 `refersh_dma_buf`。

结论：该通道不完整，暂不使用。

### 方案 2：驱动层双缓冲，每帧 `tft_spi_send()` 翻页

- 新增第二块整屏缓冲，每 16.7ms 调 `tft_spi_send(buf, 480, 480)` 翻页，并 `gpu_share_tft_init()` 切绘制目标。
- 现象：
  - 画面被拉得很长/滚动；
  - 两幅画面来回切换。
- 原因：
  - `tft_spi_send()` 会重写 `LCDSIZE` 和 `LCDCON` 启动位，等于反复重启 LCD 扫描，几何/同步被破坏 → 拉伸。
  - 显示缓冲和绘制目标切换不同步，出现新旧画面交替。

### 方案 3：只写 `LCDADR` + 切 `share_tft`（不定时重启）

- 去掉 `tft_spi_send()`，每帧只写 `LCDADR`，同时 `gpu_share_tft_init()` 指向另一块。
- 现象：
  - 两幅画面重叠；
  - 一帧始终不动，另一帧持续更新；
  - 滑动页面再滑回，其中一帧始终是旧画面。
- 分析：
  - 只改 `LCDADR` 确实能切换显示缓冲，但另一块一旦变成旧内容就不再更新；
  - 说明 GPU 的渲染目标并没有跟着运行时修改的 `share_tft` 切换（或 GUI 增量绘制导致非当前缓冲缺少完整内容）；
  - 两块缓冲内容不一致，交替显示就是“叠加/旧帧”。

### 方案 4：按 BK7258 思路，在 `LCDPEND` 帧结束时翻页

- 只在 `LCDPEND bit0` 置位时切 `LCDADR`、切 GPU 目标并 `os_gui_draw()`。
- 现象：画面能显示，但完全不动。
- 原因：这块 RGB 屏连续扫描模式下 `LCDPEND` 不会稳定置位，`os_gui_draw()` 被放在该分支里 → 第一帧之后不再请求绘制。

### 方案 5：拷贝式双缓冲（当前代码）

- 线程上下文 `lcd_480_st7701s_db_poll()`：
  1. `gpdma1_memcpy()` 把当前显示缓冲整帧拷到后台缓冲；
  2. `gpu_share_tft_init()` 把绘制目标切到后台；
  3. `os_gui_draw()` 在后台画增量；
  4. 置 `db_phase = 1`。
- TE 中断 `lcd_480_st7701s_db_refresh()`：
  1. 等 `db_phase == 1`；
  2. `LCDADR = 后台缓冲`；
  3. 交换前后台，`db_phase = 0`。
- 目的：保证后台缓冲始终是“完整画面 + 增量”，再翻页。
- 结果：**仍然不行**（用户实测反馈），具体现象待补充。

## 4. 关键静态分析结论

### 4.1 `libplatform.a(gui.o)`

- `os_gui_flush_lcd()`：user psram 模式下流程为
  `get() → 检查 gui_flush_timeout → get() → 记录 lcd_buf → tft_frame_start() → tft_spi_send_all(lcd_buf, w, h)`，
  `put()` 在 1ms 定时器里等传输结束后调用。
- `gui_flush_lcd_buff_get/put/is_user_psram` 在宏为 0 时是弱符号（`return NULL` / 空函数）。
- `os_gui_draw_w4_done()` 用于等待当前帧绘制完成。

### 4.2 `libplatform.a(tft.o)`

- `tft_spi_send()` / `tft_spi_send_all()` 对 PRGB16：
  - 写 `LCDADR = buf`；
  - 写 `LCDSIZE = (w-1) | ((h-1)<<16)`；
  - `LCDCON |= 2`（启动位）；
  - ramless 模式下不等待传输完成。
- `gpu_share_tft_init()` 只写 `share_tft`：
  - `+0`：ramless 支持标志；
  - `+1`：rgbw 支持标志；
  - `+4`：ramless framebuffer 地址（DMA 映射，`| BIT(28)`）；
  - `+8`：行宽。

### 4.3 GPU 固件 `ui/0gpu/gpu.bin`

- 固件中确实有读取 `share_tft`（0x20104/0x20108，即 ramless 标志和缓冲指针）的代码，但只出现在推流/flush 相关函数里；
- 未找到 CPU 侧可用的“切换 GPU 渲染目标”的公开接口；
- 因此运行时修改 `share_tft` 是否真正改变 GPU 绘制目标，目前存疑。

### 4.4 平台限制

- `api_sys.h` 明确：**中断里执行位于 flash 的函数会触发 CACHE/IRQ 异常复位**。
- 所有被 TE 中断调用的函数必须放在 RAM 段（如 `AT(.com_text.tft_spi)`）。
- 之前把 `lcd_480_st7701s_db_refresh()` 放在 flash 里，导致过 `CPU_ERR`（halt 8001，PCERR 指向 flash 取指）。

## 5. 当前代码改动点

- `projects/watch320/config.h`
  - `#define GUI_RGB_DOUBLE_BUF 1`（可改 0 回退单缓冲）。
- `platform/gui/tft/tft_480_st7701s_prgb.c`
  - 第二块整屏缓冲 `refersh_dma_buf2`；
  - `db_front_idx / db_back_idx / db_phase / db_ready`；
  - `db_dma_addr()`：PSRAM 地址 `| BIT(28)`；
  - `lcd_480_st7701s_db_refresh()`：TE 中断翻页（RAM 段）；
  - `lcd_480_st7701s_db_poll()`：线程上下文整帧拷贝 + 切目标 + 请求绘制；
  - `lcd_480_st7701s_db_start()`：tft 初始化完成后启动。
- `platform/gui/tft/tft.c`
  - `tft_te_refresh()`：双缓冲模式下只调 `db_refresh()`，不再单独 `os_gui_draw()`；
  - `tft_init()`：`lcd_drv_init()` / `lcd_drv_set_window()` 之后调用 `db_start()`。
- `projects/watch320/functions/func.c`
  - `func_process()` 在 `gui_process()` 之后调用 `lcd_480_st7701s_db_poll()`。

## 6. 当前结论

- 硬件支持通过写 `LCDADR` 切换整帧显示。
- 但和 BK7258 不同，本 SDK 没有暴露“指定一块 framebuffer 进行渲染”的接口；GPU 是否跟随 `share_tft` 运行时切换尚不能确认。
- 同时 GUI 是增量绘制，非当前缓冲缺内容，必须“整帧拷贝到后台再画增量”，但这套方案目前仍未调通。

## 7. 下一步建议

1. **向厂商确认**：
   - `gpu_share_tft_init()` 之后，GPU 是否每帧重新读取 `share_tft.ramless_buf`？
   - 有没有切换 GPU 渲染目标的正确接口（类似 BK 的 `lcd_display_frame_request` + 帧结束切换基地址）？
   - RGB 连续扫描下 `LCDPEND` 的正确用法/是否有 VSYNC 中断。
2. 若 GPU 目标可切：继续完善方案 5，把翻页对齐到真实 VSYNC，并确认拷贝与绘制的完成时序。
3. 若 GPU 目标不可切：考虑三缓冲 + 整帧 DMA 拷贝（GPU 固定画一块，拷贝到另一块再翻页），代价是每帧多一次约 450KB 的 PSRAM 拷贝。
4. 临时兜底：`GUI_RGB_DOUBLE_BUF = 0` 恢复单缓冲，仅在切换动画时有撕裂。
